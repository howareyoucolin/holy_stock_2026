# holyStocks

Two halves with one database:

- **`public/`** — a public PHP site that **only reads** MySQL and shows learnings
  to visitors. This is what gets deployed.
- **`app/`** — a **local-only** Next.js console for asking AI agents questions
  and writing the takeaways to the same remote MySQL. Never deployed. It also
  previews the saved rows, so the PHP site does not need to run locally.

```
   app/ (local, Next.js)                     public/ (deployed PHP)
   ask claude + codex                        read-only listing
   write takeaways  ─────►  remote MySQL  ◄─────  read
   preview rows     ◄─────   holy_stock
```

## Stack

- **PHP 8.2 + Apache** in Docker (`php:8.2-apache`, document root `public/`)
- **Next.js 16 + React 19** in `app/`, run natively on the host
- **Remote MySQL** (`mysql.369usa.com`), reached locally through an SSH tunnel

## Quick start

The MySQL user is granted only from DreamHost's own subnet, so **local access
requires the tunnel** — a direct connection is refused no matter the credentials.

```bash
cp .env.example .env      # fill in the DB user/password
npm run tunnel            # 1. open the tunnel to the remote MySQL
npm run dev               # 2. console on http://localhost:8300
```

That is the whole local workflow — the PHP site is only needed when you want to
check the public rendering:

```bash
npm run tunnel:docker            # rebind the tunnel so the container can reach it
docker compose up -d --build     # public site on http://localhost:8301
```

All npm scripts run from the project root:

| Script | What |
|---|---|
| `npm run dev` | starts the console on :8300 (UI and API together) |
| `npm run dev:stop` | stops the console (leaves the PHP site and tunnel running) |
| `npm run setup` | installs `app/` dependencies without starting anything |
| `npm run tunnel` | opens the MySQL tunnel on loopback |
| `npm run tunnel:docker` | same, but reachable by the php container |
| `npm run tunnel:stop` | closes it |

`npm run dev` installs `app/` dependencies on first run and picks a Node 20+
release from those already installed, so it works without `nvm use` first — the
shell default (Node 16) is too old for Next. It warns if the tunnel is down.

Check the site's database connection at any time:

```bash
docker exec holy_stocks_php php /var/www/html/public/health.php
```

Create the schema (once, or after adding a migration):

```bash
docker exec holy_stocks_php php /var/www/html/public/migrate.php
```

| Port | What |
|---|---|
| 8300 | Next.js console (UI + API routes) |
| 8301 | public PHP site (Docker, optional locally) |
| 13307 | SSH tunnel to the remote MySQL |

## The tunnel

`369usabc` is granted from `173.236.128.0/255.255.128.0` — DreamHost's own
network. Forwarding through the DreamHost server makes the connection arrive from
inside that subnet, which is what the grant expects.

```bash
npm run tunnel          # 127.0.0.1 only — all the Next console needs
npm run tunnel:docker   # 0.0.0.0, so the php container can reach it too
npm run tunnel:stop
```

Prefer the plain form. `--docker` binds all interfaces, because the container
reaches the host as `host.docker.internal`, which does not resolve to loopback
from inside the container — while that is open, other machines on your LAN can
reach port 13307.

Production never uses the tunnel: it talks to `mysql.369usa.com` directly, from
inside the granted subnet.

## Configuration

| Where | Reads | Used by |
|---|---|---|
| `.env` | `DB_*` env vars | php container, and `app/` (which rewrites the host to loopback) |
| `public/config.php` | array from file | production only; generated by the deploy script |

Credentials resolve in the order `DB_DSN` → individual `DB_*` vars →
`public/config.php`. All three of `.env`, `public/config.php`, and
`deploy/dreamhost.env` are gitignored.

## Layout

```
Dockerfile             php:8.2-apache, pdo_mysql, doc root -> public/
docker-compose.yml     php service only, :8301
public/index.php       public list of published learnings
public/learning.php    public detail page

public/migrate.php     migration runner
public/migrates/       one file per schema change

data/support/db.php    connect_pdo() — shared PDO factory
app/                   local-only Next.js console (see app/README.md)
bin/db-tunnel.sh       SSH tunnel to the remote MySQL
bin/dev.sh             starts the console, picking a new enough Node
deploy/                DreamHost deploy (see deploy/README.md)
```

## Database

One table, `learnings`: `title`, `question`, `takeaway`, `claude_answer`,
`codex_answer`, `is_published`, timestamps. `app/` writes rows and previews all of
them; `public/` reads only rows where `is_published = 1`.

## Migrations

Each file in `public/migrates/` returns a name and its SQL, named
`YYYY_MM_DD_HHMMSS_description.php` so they sort chronologically. Applied names
are tracked in a `migrations` table, so re-running is safe.

```php
<?php

declare(strict_types=1);

return [
    'name' => '2026_08_14_120000_create_learnings',
    'up' => <<<'SQL'
CREATE TABLE learnings (...) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
SQL,
];
```

## Deploy

Only `public/` and `data/` are synced — `app/`, `bin/`, and `deploy/` stay local.
See [deploy/README.md](deploy/README.md).

```bash
./deploy/deploy.sh --dry-run
./deploy/deploy.sh
```
